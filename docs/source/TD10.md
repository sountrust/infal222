# TD10 — Refonte du plan VLAN, mutualisation de configuration et redondance de passerelle avec HSRP

## Pré-requis

Les notions suivantes sont déjà maîtrisées :

- VLAN ;
- trunks 802.1Q ;
- sous-interfaces routeur ;
- routage inter-VLAN local ;
- interconnexion inter-routeurs via OSPF ;
- sortie WAN et redondance WAN.

Les équipements sont administrés en **console** ou en **SSH** depuis un poste Windows.

## 1. Objectif

L’architecture actuelle a gagné en robustesse sur le WAN, mais elle conserve une faiblesse locale :

la redondance de passerelle n’est pas généralisable proprement si les mêmes identifiants VLAN sont réutilisés dans plusieurs groupes.

Tant que les groupes restent strictement séparés au niveau 2, il est possible de conserver partout les mêmes tags VLAN. En revanche, dès qu’un même routeur de secours doit pouvoir reprendre plusieurs groupes via un même trunk, cette convention devient ambiguë.

L’objectif de ce TD est donc triple :

- faire évoluer le plan de numérotation VLAN pour lever cette ambiguïté ;
- réutiliser et adapter des configurations modèles afin de limiter les erreurs et homogénéiser les équipements ;
- mettre en place une redondance de passerelle avec **HSRP**.

## 2. Problème à résoudre

Jusqu’à présent, chaque groupe utilisait la même logique de tags :

- VLAN 2
- VLAN 3
- VLAN 99

avec un plan IP distinct par groupe :

- `10.g.2.0/24`
- `10.g.3.0/24`
- `10.g.99.0/24`

Cette convention est simple, mais elle devient inadaptée dès lors qu’un routeur doit porter, sur un même trunk, des VLAN provenant de plusieurs groupes.

Un tag 802.1Q identifie un VLAN.

Sur un même trunk, **VLAN 2** ne peut pas signifier à la fois :

- VLAN 2 du groupe 1 ;
- VLAN 2 du groupe 2 ;
- VLAN 2 du groupe 3.

Il faut donc adopter une numérotation **globalement unique**.

## 3. Nouvelle convention de nommage et de numérotation

Le principe retenu est le suivant :

- le tag **x** devient le tag **gx**

### Exemple

| Groupe   | VLAN utilisateurs | VLAN administration |
| -------- | ----------------: | ------------------: |
| Groupe 1 |            12, 13 |                  19 |
| Groupe 2 |            22, 23 |                  29 |
| Groupe 3 |            32, 33 |                  39 |

Le plan IP peut rester inchangé.

| VLAN    | Réseau         | Passerelle    |
| ------- | -------------- | ------------- |
| VLAN 12 | `10.1.2.0/24`  | `10.1.2.254`  |
| VLAN 13 | `10.1.3.0/24`  | `10.1.3.254`  |
| VLAN 19 | `10.1.99.0/24` | `10.1.99.254` |
| VLAN 22 | `10.2.2.0/24`  | `10.2.2.254`  |
| VLAN 23 | `10.2.3.0/24`  | `10.2.3.254`  |
| VLAN 29 | `10.2.99.0/24` | `10.2.99.254` |
| VLAN 32 | `10.3.2.0/24`  | `10.3.2.254`  |
| VLAN 33 | `10.3.3.0/24`  | `10.3.3.254`  |
| VLAN 39 | `10.3.99.0/24` | `10.3.99.254` |

Cette évolution montre qu’un **ID de VLAN** et un **plan d’adressage IP** sont deux éléments distincts.

## 4. Architecture cible

L’architecture finale doit permettre :

- des VLAN localement présents sur les switches de chaque groupe ;
- une numérotation VLAN non ambiguë ;
- un routeur principal et un routeur de secours pour certains VLAN ;
- une passerelle virtuelle unique côté clients grâce à **HSRP**.

### Principe général

- chaque groupe dispose de ses VLAN renommés ;
- les trunks et sous-interfaces sont adaptés au nouveau plan ;
- les équipements de commutation réutilisent une base de configuration commune, adaptée localement ;
- les hôtes n’utilisent plus une IP physique de routeur comme passerelle, mais une **IP virtuelle HSRP**.

```{mermaid}
flowchart LR
    subgraph LAN[LAN du groupe]
        PC1[Poste 1]
        PC2[Poste 2]
        SW[Switch / VLAN remappés]
        PC1 --> SW
        PC2 --> SW
    end

    SW --> VIP[Passerelle virtuelle HSRP]
    VIP --> RMAIN[Routeur principal]
    VIP -. secours .-> RSEC[Routeur de secours]
```

## 5. Travail demandé

Le TD se déroule en trois phases :

### Phase A — Remapping VLAN

Faire évoluer le plan VLAN existant vers une numérotation unique à l’échelle de l’infrastructure.

### Phase B — Mutualisation de configuration

Préparer une base de configuration réutilisable pour les switches, puis l’adapter par copie contrôlée via console ou SSH.

### Phase C — HSRP

Mettre en œuvre une redondance de passerelle sur les VLAN concernés.

## Phase B — Mutualisation de configuration

## 10. Principe

Dans une infrastructure où plusieurs switches remplissent des rôles proches, il est inefficace de tout reconfigurer entièrement à la main.

L’objectif est de :

- sauvegarder la configuration actuelle ;
- préparer une configuration modèle ;
- la réutiliser par copie contrôlée en console ou en SSH ;
- l’adapter localement.

Il ne s’agit pas ici d’automatisation avancée, mais d’une première démarche de **standardisation**.

## 11. Sauvegarde préalable

Avant toute modification :

```text
show running-config
copy running-config startup-config
```

## 12. Construction d’une configuration modèle

Préparer une base de configuration adaptée au rôle du switch, par exemple :

- création des VLAN ;
- nommage cohérent ;
- configuration des trunks ;
- configuration des ports access ;
- éventuelles commandes STP déjà connues.

### Exemple de base de configuration

```text
conf t
vlan 12
 name G1_VLAN2
vlan 13
 name G1_VLAN3
vlan 19
 name G1_VLAN99
interface fa0/1
 switchport mode trunk
 switchport trunk allowed vlan 12,13,19
interface range fa0/2 - 10
 switchport mode access
 switchport access vlan 12
 spanning-tree portfast
end
wr mem
```

## 13. Réutilisation

La configuration modèle peut être :

- copiée dans un fichier texte sur le poste Windows ;
- collée ensuite par blocs cohérents dans la console ou la session SSH ;
- adaptée immédiatement selon :
  - le nom du switch ;
  - les interfaces réellement utilisées ;
  - les VLAN autorisés ;
  - le rôle du switch dans l’architecture.

## 14. Bonne pratique

Coller la configuration par blocs :

1. VLAN et noms ;
2. trunks ;
3. ports access ;
4. paramètres complémentaires.

Vérifier à chaque étape :

```text
show running-config
show vlan brief
show interfaces trunk
```

## Phase C — Redondance de passerelle avec HSRP

## 15. Définition

**HSRP** (_Hot Standby Router Protocol_) est un protocole de redondance de premier saut.

Il permet à plusieurs routeurs de présenter aux hôtes :

- une **passerelle virtuelle unique** ;
- alors qu’en réalité plusieurs routeurs sont présents.

### Principe

- un routeur est **active** ;
- un autre est **standby** ;
- les clients utilisent une **IP virtuelle** comme passerelle ;
- si le routeur actif tombe, le standby prend le relais.

```{mermaid}
flowchart LR
    H1[Hôte] --> VIP[Passerelle virtuelle HSRP]
    H2[Hôte] --> VIP
    VIP --> RA[Routeur active]
    VIP -. secours .-> RS[Routeur standby]
```

## 16. Éléments de configuration

Pour chaque VLAN concerné, il faut définir :

- un numéro de groupe HSRP ;
- une IP virtuelle ;
- une priorité ;
- la préemption.

### Convention conseillée

Utiliser comme IP virtuelle l’adresse **`.254`**, et déplacer les adresses physiques des routeurs.

### Exemple — Groupe 1

- **R1 physique** : `10.1.2.252`
- **R3 physique** : `10.1.2.253`
- **HSRP virtuelle** : `10.1.2.254`

Même logique pour les autres VLAN retenus.

## 17. Exemple de configuration HSRP

### Sur le routeur principal

```text
conf t
interface g0/1.12
 encapsulation dot1Q 12
 ip address 10.1.2.252 255.255.255.0
 standby 12 ip 10.1.2.254
 standby 12 priority 110
 standby 12 preempt
end
wr mem
```

### Sur le routeur de secours

```text
conf t
interface g0/1.12
 encapsulation dot1Q 12
 ip address 10.1.2.253 255.255.255.0
 standby 12 ip 10.1.2.254
 standby 12 priority 100
 standby 12 preempt
end
wr mem
```

Le même principe doit être reproduit sur les autres VLAN retenus pour la redondance.

## 18. Vérifications HSRP

```text
show standby brief
show standby
show ip interface brief
```

Vérifier :

- quel routeur est **active** ;
- quel routeur est **standby** ;
- que l’IP virtuelle est bien annoncée ;
- que les hôtes utilisent désormais cette IP comme passerelle par défaut.

## 19. Tests de fonctionnement

### Test 1 — Connectivité normale

Depuis un poste client :

- ping vers la passerelle virtuelle ;
- ping vers un poste d’un autre VLAN ;
- ping vers un réseau distant.

### Test 2 — Bascule

Sur le routeur actif, provoquer une panne contrôlée :

```text
conf t
interface g0/1
 shutdown
end
```

ou, selon l’architecture retenue, sur la sous-interface ou le lien concerné.

Puis vérifier :

```text
show standby brief
```

Le routeur de secours doit devenir **active**.

### Test 3 — Retour à la normale

```text
conf t
interface g0/1
 no shutdown
end
```

Avec `preempt`, le routeur prioritaire peut reprendre son rôle d’actif.

## 21. Synthèse

Dans ce TD :

- le plan VLAN évolue vers une numérotation globale et cohérente ;
- les configurations sont mutualisées à partir d’une base réutilisable ;
- la redondance de passerelle est introduite avec **HSRP** ;
- les clients utilisent désormais une **passerelle virtuelle** ;
- l’architecture locale gagne en disponibilité.

Cette évolution montre qu’une architecture réseau ne se contente pas d’être fonctionnelle : elle doit aussi rester **lisible**, **maintenable** et **résiliente**.
